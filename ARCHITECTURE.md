# Architecture

## Shape of the app

```
index.html
  └── src/main.tsx            picks a TaskStore, mounts <App>
        └── src/App.tsx       gate vs. task UI, active tab, which dialog is open
              ├── src/store.ts            useTaskTracker(): state + persistence
              │     ├── src/mutations.ts  pure (TaskFile, …) => TaskFile
              │     └── src/storage/*     the TaskStore implementations
              └── src/components/*        presentational, no persistence
```

Supporting pure modules: `src/types.ts` (the data model), `src/quadrants.ts`
(the only place the four urgent/important combinations are written down),
`src/ordering.ts` (sort keys), `src/dates.ts` (local calendar days),
`src/schema.ts` (parse/serialize the file, with repairs).

## Data flow

1. `main.tsx` constructs a `TaskStore` — normally `FileSystemStore`, or a test
   seam for a dev build (see TESTING.md).
2. `useTaskTracker` calls `store.init()`. If a file is remembered and still
   permitted, it loads it; otherwise `App` renders `GateScreen`.
3. A user action calls an action from the hook, e.g. `actions.setQuadrant(id, 'q2')`.
4. The hook applies the matching pure mutation to the in-memory `TaskFile`,
   renders immediately, and schedules a debounced (300 ms) `store.save()`.
5. `save()` refuses to write if the file changed underneath; the refusal
   becomes `state.conflict`, and `ConflictDialog` asks the user to reload or
   overwrite.

Derived views (`tasksInQuadrant`, `completedTasks`, `openCounts`) are computed
from the `TaskFile` on render. There is no second copy of the task list.

## The storage seam

```ts
interface TaskStore {
  init(): Promise<StoreStatus>;
  status(): StoreStatus;                   // unsupported | disconnected | needs-permission | ready
  connect(mode: 'open' | 'pick' | 'create'): Promise<StoreStatus>;
  disconnect(): Promise<void>;
  load(): Promise<{ file: TaskFile; problems: string[] }>;
  save(file: TaskFile): Promise<SaveResult>;   // may return a conflict
  overwrite(file: TaskFile): Promise<SaveResult>;
  describe(): { name: string } | null;
}
```

Implementations:

- **`FileSystemStore`** — production. Uses `showOpenFilePicker` /
  `showSaveFilePicker`, stores the resulting handle through `handleDb.ts`
  (IndexedDB), checks `queryPermission` / `requestPermission`, and writes with
  `createWritable`. Its view of the File System Access API is the narrow
  `src/storage/fsa.ts` interface, not the DOM lib, which is what makes it
  testable against a fake handle.
- **`MemoryStore`** — a string instead of a file. Used by unit tests and the
  Playwright UI suite.

`connect` modes: `open` re-grants the remembered file (no picker when one is
remembered), `pick` always shows the open picker ("Change file…"), `create`
shows the save picker pre-named `task-tracker-task.json`.

## Conflict detection

Each successful read or write records `(file.lastModified, revision)`. Before
writing, `save()` re-reads the file: if `lastModified` differs **and** the
on-disk `revision` differs from the remembered one, the write is refused and
the on-disk version is returned as a conflict. Comparing the revision as well
as the timestamp means a sync client touching the file without changing it does
not raise a false conflict.

Resolution is the user's: *Reload from file* discards local edits,
*Overwrite with my changes* calls `overwrite()`, which skips the check.

## Why File System Access

The requirement is a configurable JSON file in the user's home folder, shared
between machines. Three options were weighed:

| Approach | Default path without a dialog | Extra moving parts | Verdict |
| --- | --- | --- | --- |
| **File System Access API** | No — one picker on first run, one click per session | None; stays a pure PWA | **Chosen** |
| Localhost Node sidecar | Yes | A second process to keep alive (launchd), app no longer self-contained | Rejected |
| Tauri desktop app | Yes | Rust toolchain, not a PWA any more | Rejected |

The cost of the chosen approach is the gate screen and Chrome/Edge only. If the
dialog-free default path ever becomes the priority, the sidecar is the smallest
step: write a `TaskStore` that talks to `http://localhost:<port>` and change
one line in `main.tsx`. Nothing above the seam would change.

## PWA

`vite-plugin-pwa` in `generateSW` mode with `registerType: 'autoUpdate'`
precaches the built shell, so the installed app opens offline. The manifest
(name, standalone display, three icons) lives in `vite.config.ts`; the icons in
`public/` are generated by a dependency-free script — see CONTRIBUTING.md.
There is no network dependency at runtime: the data is a local file.
